# 0002. Redis는 아직 도입하지 않는다 — 운영 메트릭으로 다시 판단할 기준

## 배경
운영 메트릭(#76)을 붙이면서 "캐시·공유 상태를 Redis로 옮길 때가 됐나"를 같이 정리한다. 지금 Redis가
맡을 수 있는 후보는 셋이다.

1. **외부 API 응답 캐시** — TAGO 도착예측·KLID 신호 상태를 짧은 TTL로 캐시해 공공데이터포털 일 한도를 아끼는 것
2. **메모리에만 있는 상태의 보존·공유** — 외부 호출 집계(`ExternalCallStore`), KLID NODATA 건너뛰기 표시
   (`KlidNoDataRegistry`, #31), 폴링·보관 배치의 마지막 실행(`BatchRunTracker`). 지금은 재시작하면 비고,
   인스턴스가 둘이면 서로 모른다
3. **분산 잠금** — 인스턴스가 여럿일 때 폴링 스케줄러가 한 번만 돌게 하는 것

현재 상황 (2026-10):
- 1인 사용, backend 인스턴스 하나(compose 한 대). 폴링은 출퇴근 창(하루 6시간)에만 60초 간격
- 호출량은 "활성 경로의 버스 구간 수 + 신호 지자체 수 × 페이지 수"로 정해지고 사용자 요청 수와 상관없다
  (ARCHITECTURE "호출 한도"). 앱이 화면을 열 때마다 외부 API를 부르지 않는다 — 추천·관측은 이미 Postgres
  테이블(`departure_recommendations`, `transit_arrival_observations`, `traffic_signal_states`)이 캐시 역할을 한다
- 한도: 개발계정 기준 TAGO 오퍼레이션마다 일 1,000회, KLID 일 5,000회 수준 (`wio.tago.daily-limit`,
  `wio.klid.daily-limit`)
- 재시작해서 잃는 것은 "오늘 집계"와 "NODATA 표시"뿐이고, 둘 다 다음 사이클·다음 날에 저절로 복구된다

## 결정
**지금은 Redis를 도입하지 않는다.** 위 세 후보 모두 현재 규모에서는 비용(컨테이너 하나 + 장애 지점 하나 +
직렬화·TTL 설계)이 이득보다 크다.

- 외부 API 캐시: 같은 (정류장, 노선)이나 지자체를 한 사이클 안에서 두 번 부르지 않으므로 캐시할 중복이 없다.
  한도를 아끼는 수단은 이미 폴링 창·활성 경로 한정·NODATA 건너뛰기(#31)로 쓰고 있다
- 메모리 상태: 잃어도 정확성에 영향이 없다(관측 데이터는 Postgres에 있다). 운영 화면은 "집계 시작" 시각을 보여
  주므로 재시작 직후의 0을 오해하지 않는다
- 분산 잠금: 인스턴스가 하나다

## 다시 판단할 기준
아래 중 하나라도 충족되면 이 ADR을 다시 연다. 판단 근거는 운영 화면(desktop "운영",
`GET /api/v1/admin/ops/external-apis`)의 값이다 — 재시작하면 비는 메모리 집계이므로, 며칠에 걸친 판단은
그날그날 화면(또는 JSON 로그의 `polling cycle` 줄)을 보고 기록해 둔다.

| 신호 | 기준 | 그때 검토할 것 |
|---|---|---|
| 한도 사용률 | 어떤 op든 **오늘 사용률 70% 초과가 영업일 3일 연속** (운영 화면 막대의 "한도 70%+" 표시) | 외부 응답 짧은 TTL 캐시(Redis 또는 먼저 Caffeine 같은 프로세스 내 캐시), 폴링 간격·대상 재조정, 운영계정 신청 |
| 한도 초과 | `api_error`가 한도 초과 결과 코드(TAGO `22`, KLID `K22`)로 **한 번이라도** 남음 | 위와 같음. 이것은 즉시 조치 대상 |
| 중복 호출 | 같은 (op, 파라미터)를 1분 안에 두 번 이상 부르는 경로가 생김 — 예: 앱이 화면을 열 때마다 실시간 조회(ARCHITECTURE "확장 여지") | 외부 응답 캐시 |
| 인스턴스 수 | backend를 둘 이상 띄움 | 폴링 분산 잠금(또는 ShedLock + Postgres), 집계·NODATA 표시 공유 |
| 재시작 손실 | 재시작 때문에 한도 판단을 못 한 날이 한 달에 두 번 이상 | 집계를 Postgres나 Redis로 영속화 |

먼저 고려할 대안은 Redis가 아니라 **이미 있는 Postgres**(ShedLock, 집계 테이블)와 **프로세스 내 캐시**다.
Redis는 그 둘로 부족할 때(여러 인스턴스가 같은 캐시를 봐야 하는데 Postgres 부하가 문제일 때) 고른다.

## 결과
- 이 PR은 Redis 없이 메모리 집계(`ExternalCallStore`)와 Micrometer Timer(`wio.external.calls`)를 둔다
- ARCHITECTURE "확장 여지"의 Redis 항목은 이 ADR을 가리킨다
