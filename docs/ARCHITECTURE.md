# 아키텍처 개요

## 문제 정의

출퇴근길에 광역버스/GTX/지하철처럼 배차 간격이 길고 놓치면 큰 손해(다음 차 20~30분 대기)인
교통수단을 탄다. "언제 집에서 나가야 하는가"를 매일 감으로 정하는 대신, 다음 데이터를
기반으로 계산한다.

- 버스/지하철/GTX의 (실시간 예측 or 정적 시간표) 도착 시각
- 각 정류장/역까지 걸어가는 데 걸리는 시간 (개인 평균 도보 속도 기반)
- 도보 경로 중간의 신호등 대기 시간
- 과거에 "탔다/못 탔다"를 기록한 실측 데이터 (위 예측들의 오차를 보정하는 데 사용)

출력은 "OO시 OO분까지 나가면 P%의 확률로 그 차를 탄다" 형태의 추천이다.

## 컴포넌트 구성

```
                       ┌─────────────────────────┐
                       │   외부 공공데이터 API     │
                       │ (TAGO 버스, 지하철 실시간,│
                       │  신호운영 데이터 등)      │
                       └────────────┬─────────────┘
                                    │ 주기적 동기화 (스케줄러)
                                    ▼
┌───────────┐   REST   ┌─────────────────────────┐   내부 API/배치   ┌──────────────┐
│ iOS 앱     │ ───────▶ │  Backend (Kotlin/Spring) │ ─────────────▶  │ Analytics     │
│ (Swift)   │ ◀─────── │  - API 서버              │ ◀─────────────  │ (Python)      │
│ GPS 수집   │  추천 결과│  - 도메인/DB 관리         │  프로필/추천 결과 │ - 도보속도 추정 │
│ 탑승 기록  │          │  - 외부 API 동기화 잡     │                 │ - 신호 보정    │
└───────────┘          └────────────┬─────────────┘                 │ - 예측 오차 보정│
                                    │                                │ - 최적 출발시간 │
                                    ▼                                │   계산 모델    │
                       ┌─────────────────────────┐                  └──────────────┘
                       │      PostgreSQL          │
                       │  (docs/db/schema.sql)   │
                       └────────────┬─────────────┘
                                    ▲
                                    │ REST (조회 전용)
                       ┌─────────────────────────┐
                       │ 데스크탑 웹 (TS/React)    │
                       │ - 경로/정류장 관리 UI     │
```

### iOS 앱 (Swift)
- 등록된 출퇴근 경로(집 → 정류장/역 → 목적지)에 대해 백그라운드 위치 수집
  (Significant Location Change + 정류장 근처 Geofence로 배터리 절약)
- "탑승 시도" 이벤트 기록: 자동 감지(정류장 geofence 진입 후 일정 속도로 이동 시작 =
  탑승 추정) + 사용자가 직접 탔다/못 탔다를 눌러 보정
- GPS trace, 탑승 기록을 backend에 업로드
- backend가 계산한 "언제 나가야 하는지" 추천을 알림/위젯으로 표시

### Backend (Kotlin + Spring)
- 도메인 모델의 단일 진실 소스(source of truth), REST API 제공
- 외부 공공데이터 API(TAGO 국가교통정보센터 버스도착정보, 서울 열린데이터광장 지하철
  실시간, 신호운영 데이터 등)를 스케줄러로 주기 동기화 → `transit_schedules`,
  `transit_arrival_observations`에 적재
- GTX처럼 실시간 API가 없거나 커버리지가 낮은 노선은 정적 시간표 + 사용자 실측 기록으로
  대체(fallback)
- 분석 결과(도보 프로필, 추천 출발 시각)는 Analytics가 채운 테이블을 그대로 읽어서
  API로 노출 (backend는 무거운 통계 계산을 직접 하지 않음)

### Analytics (Python)
- 배치/주기 작업으로 실행 (처음엔 cron, 필요해지면 Airflow 등으로 확장 가능)
- 네 가지 축의 보정 모델을 유지:
  1. **도보 속도 프로필**: trip/attempt의 인접 사건 시각과 GPS trace → 구간별 실제 도보
     시간 추출 → 사용자별/구간별 평균·표준편차 갱신
  2. **교통수단 도착 예측 오차**: 외부 API의 "예상 도착시간" vs 실측 탑승 기록의
     "실제 출발시간" 차이를 노선/정류장/시간대별로 누적 → bias, variance 추정
  3. **차내 이동시간**: 탑승 시각 → 하차 시각 실측으로 승차역-하차역 소요시간 분포 추정
  4. **신호등 대기**: 신호 주기 데이터(공공데이터 or 사용자 관찰) → 횡단보도별
     기대 대기시간 추정
- 위 모델을 합쳐 `docs/ALGORITHM.md`의 방식으로 "최적 출발 시각"을 계산하고
  `departure_recommendations`에 기록
- 알고리즘 상세: [ALGORITHM.md](./ALGORITHM.md)

### 데스크탑 웹 (TS/React)
- 조회·관리 중심 (경로/정류장/신호등 등록, 기록 히스토리, 캘리브레이션 상태 확인)
- 실시간 GPS 수집은 하지 않음 (그건 앱의 역할)

## 데이터 흐름 요약

1. 사용자가 데스크탑에서 출퇴근 경로(도보 → 버스 → 도보 → 지하철 → 도보 등)를 등록
2. 앱이 매일 그 경로를 따라 이동하며 GPS를 수집하고 탑승 시도를 기록
3. Backend가 외부 API로 노선 시간표/실시간 예측을 계속 동기화
4. Analytics가 주기적으로 (a) 도보 속도, (b) 교통수단 예측 오차, (c) 신호 대기를
   보정하고, 목표 시각(예: 회사 도착 목표 시각)에 맞는 "언제 나가야 하는지"를 계산
5. 앱/웹이 그 추천을 사용자에게 보여줌 → 사용자가 그대로 따르거나 벗어난 결과가
   다시 1의 기록으로 쌓여 모델이 계속 좋아짐 (피드백 루프)

## 왜 이 스택인가

- **Kotlin/Spring**: 도메인 모델이 명확한 CRUD + 스케줄러 + REST API에 적합, 정적 타입으로
  스키마 변경 시 안전
- **Python (Analytics)**: 통계/시계열 보정(pandas, numpy, scipy 등)에 생태계가 압도적으로
  유리. Backend와 분리해 두면 모델 로직을 자유롭게 바꿔도 API 계약이 안 깨짐
- **Swift 앱**: 백그라운드 위치 수집 품질(정확도, 배터리)은 네이티브가 유리하며,
  이 프로젝트의 핵심 데이터(GPS)가 여기서 나옴
- **TS/React 데스크탑**: 관리/조회 화면은 굳이 네이티브일 필요 없음, 웹으로 빠르게

## 확장 여지 (지금 범위 아님)

- GTX-A 등 실시간 API가 아직 없는 노선은 정적 시간표 기반으로 시작하고, 실측 기록이
  쌓이면 자동으로 보정 정확도가 올라가는 구조로 설계했으므로 나중에 실시간 API가
  열려도 스키마 변경 없이 `transit_arrival_observations`에 소스만 추가하면 됨
- 여러 사용자를 지원하는 구조지만 지금은 1인 사용 기준으로 단순화 가능
- Redis 등 별도 캐시는 두지 않는다. 캐시가 필요한 값(외부 API 응답, 최신 추천)은 이미
  `transit_arrival_observations`/`departure_recommendations` 테이블이 그 역할을 하고, 1인
  규모에선 Postgres 조회로 충분. 앱에서 "지금 몇 분 남았어?"를 초 단위로 폴링하게 되어
  공공 API 호출 한도가 문제 되는 시점에 짧은 TTL 캐시로 추가 검토
